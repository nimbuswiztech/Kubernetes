Kubernetes Deployment Strategies

Welcome to the ultimate guide for teaching Kubernetes Deployment Strategies. This interactive guide breaks down the four most common methods to roll out applications in Kubernetes, complete with visual explanations, pros, cons, and when to use them.

1. Recreate Strategy

The Recreate strategy terminates all currently running instances of an application before creating new ones. This means there is a period of downtime where no instances are serving traffic.

How it works

Kubernetes scales down the existing ReplicaSet to 0, waits for pods to terminate, and then scales up the new ReplicaSet to the desired number of replicas.

Advantages

  • Extremely simple to setup.
  • Application state is entirely renewed.
  • No backward compatibility issues (v1 and v2 never run at the same time).

Disadvantages

  • Guaranteed downtime.
  • User experience is heavily impacted during the deployment window.

YAML Snippet

spec:
  replicas: 3
  strategy:
    type: Recreate

2. Rolling Update Strategy

The Rolling Update strategy (default in Kubernetes) updates Pods in a rolling fashion, rather than all at once. It gradually replaces old Pods with new ones, ensuring that the application remains available during the rollout.

How it works

Kubernetes scales up a new ReplicaSet while simultaneously scaling down the old one. It uses maxSurge and maxUnavailable to control the rollout pace.

Advantages

  • Zero downtime deployment.
  • Built-in and default behavior of Kubernetes Deployments.
  • Slow rollout allows for monitoring of errors.

Disadvantages

  • Rollout/rollback can take time.
  • v1 and v2 run simultaneously; requires backward compatibility (e.g. database schemas).

YAML Snippet

spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0

3. Blue / Green Deployment

A Blue/Green deployment involves running two identical environments. 'Blue' is the current live environment, and 'Green' is the new version. Traffic is switched over from Blue to Green all at once at the load balancer or service level.

How it works

Deploy a new ReplicaSet (Green) while the old one (Blue) is still serving traffic. Once Green is ready and tested, update the Service selector to point to Green.

Advantages

  • Instant rollout and instant rollback.
  • No version conflict (v1 and v2 are completely separate).
  • Allows for comprehensive testing on Green before go-live.

Disadvantages

  • Requires 2x the resources (costly).
  • Stateful applications can make database cutovers difficult.

Implementation Concept

# Change the service selector from:
selector:
  app: my-app
  version: v1 # Blue

# To:
selector:
  app: my-app
  version: v2 # Green

4. Canary Deployment

A Canary deployment rolls out the new version to a small subset of users before rolling it out to the entire infrastructure and making it available to everybody.

How it works

Deploy a small number of Pods running the new version alongside the stable version. Both share the same Service, so traffic is distributed between them (e.g., 90% stable, 10% canary).

Advantages

  • Test in production with real user traffic.
  • Risk is minimized (only affects a small % of users).
  • Easy to rollback if error rates spike.

Disadvantages

  • Slow rollout process.
  • Requires complex traffic management (e.g. Istio or NGINX Ingress for exact % control).

Implementation Concept

# Stable Deployment
replicas: 9
labels:
  app: my-app
  track: stable

# Canary Deployment
replicas: 1
labels:
  app: my-app
  track: canary

# Service (matches both)
selector:
  app: my-app
